# 前十榜单 10 秒采样与独立事件存储

采用普通 MongoDB 集合，每次采样一份小文档。**不显式分块，没有小时数组、bucket、part 或 revision。每个 UTC 小时首次成功采样写 FULL，作为查询检查点。** 活动前十、月榜前十默认每 10 秒采样，月榜错开 5 秒；榜线和歌曲榜默认每 60 秒存储。

10 秒是调度目标。慢请求不会叠加或补发积压请求，上游缓存也可能返回相同榜单；记录的是实际观测结果，不能推断两次观测之间发生的变化。

## 事件格式

集合：`ranking_top_events_v2`，范围键 `s` 为 `服务器/e或m/期次`，例如 `3/e/322`、`3/m/20`。

```js
{ _id: "l:3/e/322:1788912000000", s: "3/e/322", t: 1788912001234,
  a: 1788912000000, i: 10000, k: 0, d: [[1001, 500], [1002, 400]] }
{ _id: "l:3/e/322:1788912010000", s: "3/e/322", t: 1788912011250,
  a: 1788912010000, i: 10000, k: 1, d: [[2, 450]] }
{ _id: "l:3/e/322:1788912020000", s: "3/e/322", t: 1788912021180,
  a: 1788912020000, i: 10000, k: 2 }
{ _id: "l:3/e/322:1788912030000", s: "3/e/322", t: 1788912040230,
  a: 1788912030000, i: 10000, k: 3, r: "timeout" }
```

`t` 是响应完成或失败时刻，`a` 是计划采样时刻，`i` 是目标间隔，均为毫秒。迁移的历史没有可靠计划时刻，不补造 `a`。`e` 可记录终榜生效时间 `endAt`；`g: [首次缺测槽, 最后缺测槽]` 表示上次执行到本次执行之间跳过的计划槽。

| k | 类型 | 内容与含义 |
|---|---|---|
| 0 | FULL | `d` 为按名次排序的 `[UID, 绝对分数]` 完整数组 |
| 1 | PATCH | `d` 为 `[从 1 开始的名次, 新绝对分数]`；仅有序 UID 列表相同才能使用 |
| 2 | SAME | 完整有效响应与前次状态一致，仍保留本次成功时刻 |
| 3 | GAP | 本次尝试失败或服务不可用；`r` 保存原因，不产生有效 points |

FULL 条件还包括首次采样、进程重启后首次成功、故障/缺测恢复、人数/成员/次序改变，以及全部玩家分数都改变。同分换序不可忽略；合法分数回退可用绝对分数表示。不足十人允许保存，显式空数组允许保存，缺少 Top 字段或重复 UID 则拒绝。

索引为 `_id` 唯一索引、`{s:1,t:1,_id:1}` 时间索引，以及只包含 `k=0` 的 `{s:1,t:-1,_id:-1}` 检查点索引。单个 FULL 至多十人，不会随活动持续时间增长为大文档。旧格式的八日大数组仍受 MongoDB 16 MiB 单文档限制。[MongoDB 限制](https://www.mongodb.com/docs/manual/reference/limits/)

## 成功、失败和断线

1. 保留游戏接口现有的 CN RID 串行锁、405 修正和错榜标记校验重试；一次内部重试仍归属同一次采样。Top 还校验 UID、人数和分数。上游没有提供可验证的期次/生成时间时，不宣称已验证这些字段。
2. 获取并验证完整榜单，先将原始观测（完整 Top 和玩家资料）写到本地 outbox。临时文件写入、fsync、rename、目录 fsync 完成后才承认已持久化到本机。
3. 一个串行消费者按时间处理队列：从最近已提交状态编码，仅在玩家资料变化时更新 `ranking_players`，然后插入一个事件，使用 `w:1,j:true`。事件唯一 ID 提供重试去重。
4. MongoDB 确认提交后才推进内存中的已提交状态、删除队列文件。若写入成功但回执丢失，重试先查 `_id`；已存在就不重复写。无需多文档事务，适用于当前 standalone MongoDB。
5. MongoDB 失败时保留队列，默认每 5 秒重试；默认容量 64 MiB、最多 50,000 文件，达到上限会暂停采样。outbox 必须挂持久卷；单机磁盘自身损坏不在这个持久化保证内。
6. GAP 原因包括 `timeout`、`http_error`、`rejected`、`unavailable`、`fetch_error`。进程停机或任务仍在执行时没有真正发出请求，以恢复后记录的 `g` 标记缺测槽，绝不补成 SAME。尚未恢复的尾部缺测可由最近成功时刻和当前时间判断为 stale。
7. 榜线/歌曲榜的写入单独限频、只允许一个执行中的任务；它们失败不会把成功的 Top 写成 GAP，也不会堵塞 Top 采样。

当前部署按**单个采集实例**设计。不可通过增加相同账号的副本来并行写同一个范围的增量链；多实例需要另加所有权/租约控制。采集失败和数据库写入失败是两类故障，后者通过待提交队列和存储错误状态反映。

## 查询

- `GET /api/top/latest?server=3&kind=event&periodId=322`：最新已提交榜单、玩家资料、`lastAttemptAt`、`lastSuccessAt`、`lastFullAt`、`failed`、`stale`、全局 `pendingObservations` 和 `lastStorageFailureAt`。
- `GET /api/top/history?server=3&kind=monthly&periodId=20`：一次返回该期全部历史（`from=0`，`to` 为请求时刻），按时间升序排列，无分页、条数上限或 `nextCursor`。可显式传入 `from`、`to` 指定毫秒时间范围。响应为 `{scope, from, to, baseline, samples}`；`baseline` 是起点前的状态，`samples` 带 FULL/PATCH/SAME/GAP 类型、完整成功快照及缺测/失败原因。旧的 `limit`、`cursor` 参数不再参与查询。
- 查询先用索引寻找起点之前最近的 FULL，再重放到范围内；正常情况下前置重放不超过一个小时。长时间连续失败期间没有可造的 FULL，失败尾部可能更长。
- 旧 `/eventtop/data`、`/monthlyRanking/top` 保持 `{points,users}` 形状，展开每次成功观测；不为失败补点。终榜修订保留每次真实观测，但兼容视图只取最新的 `endAt` 快照。
- 新历史接口通过 MongoDB 游标逐条解码，并随 HTTP 背压输出同一个完整 JSON 响应；客户端一次请求即可取得全部数据，服务端不必把整期展开结果同时放在内存里。客户端断开时关闭数据库游标。旧接口继续整期返回 `{points,users}`。

## 参数和部署

```dotenv
TOP_HISTORY_V2_ENABLED=true
EVENT_TOP_POLL_INTERVAL_MS=10000
MONTHLY_TOP_POLL_INTERVAL_MS=10000
TOP_POLL_PHASE_OFFSET_MS=5000
BORDER_PERSIST_INTERVAL_MS=60000
GARUPA_HEALTH_CACHE_MS=30000
TOP_OUTBOX_DIR=data/top-outbox
TOP_OUTBOX_MAX_BYTES=67108864
```

Compose 挂载 `grp-speed-data:/app/data`；镜像的 `/app/data` 归 UID 1000 的 node 用户所有。健康检查缓存 30 秒，业务异常后重新检查。元数据轮询保留原有周期。终榜的低频复核沿用现有每小时配置。

需临时降低上游请求频率时，将两个 `*_TOP_POLL_INTERVAL_MS` 改回 `60000`，继续使用 V2。`TOP_HISTORY_V2_ENABLED=false` 会恢复旧读写路径，**不能作为已经写入 V2 后的无损回滚方式**。

## 旧历史兼容

旧格式的 `event_top_points`、`monthly_top_points` 集合保留。每个范围通过 `ranking_top_meta_v2` 中的 `legacyMigrated` 标记表示历史转换已完成；该标记只能在整个范围的数据写入并校验通过后设置。

标记之前，旧接口合并 V1 历史与 `l:` 实时观测，不会把部分转换结果当作完整历史。标记之后使用 V2。以后补充旧格式历史时，需要同步处理受影响的 V2 范围及完成标记。
